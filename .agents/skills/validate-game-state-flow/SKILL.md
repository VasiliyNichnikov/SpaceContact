# Validate Game State Flow

Проверить архитектурную границу изменения игрового состояния. Выполнять семантический анализ C#-кода, а не проверку только по именам методов или регулярным выражениям.

## Аргумент

Принимать ровно один аргумент:

- `all` — проверить всю цепочку `GameAction -> GameContext -> GameEvent` во всём проекте.
- `diffs` — проверить только добавленные и изменённые классы `GameAction` и `GameEvent`, включая staged, unstaged и untracked C#-файлы.

Если аргумент отсутствует или не поддерживается, не запускать проверку и попросить указать `all` или `diffs`.

## Обязательные инварианты

1. `GameAction` имеет право читать `GameContext`, выполнять бизнес-валидацию и создавать `GameEvent`.
2. `GameAction` не имеет права изменять `GameContext` прямо или косвенно.
3. `GameEvent` применяет уже проверенное изменение состояния. Он не выполняет бизнес-валидацию, не отклоняет данные и не выбирает между успехом и ошибкой.
4. Применение `GameEvent` не должно падать из-за данных события или текущего состояния. Все необходимые предусловия обязан проверить `GameAction` до создания события.
5. Игровое состояние изменяется через `GameEvent`. Прямое изменение `GameContext` в обход события считать нарушением при полной проверке.

Не считать нарушением чтение контекста для формирования результата, сериализации или маршрутизации события, если это чтение не валидирует и не изменяет игровой state.

## Определение области проверки

### Режим `all`

1. Найти интерфейсы и базовые типы действий и событий (`IGameAction`, `BaseGameAction`, `IGameEvent`, `PublicGameEvent`) и не полагаться только на суффиксы имён или каталоги.
2. Найти все конкретные реализации действий и событий.
3. Найти `GameContext`, вложенные контексты, хранимые state-объекты и методы, вызываемые из действий или событий.
4. Проследить для каждого действия чтения контекста, валидацию, создаваемые события и их `Apply`-цепочки до фактической мутации.
5. Найти записи в игровой state вне `GameEvent` и проверить, не обходят ли они событийную границу. Загрузку snapshot/bootstrap считать отдельным допустимым путём только тогда, когда код явно восстанавливает состояние, а не обрабатывает игровое действие.

### Режим `diffs`

1. Получить C#-файлы, отличающиеся от `HEAD`, включая staged и unstaged изменения, например через `git diff --name-only --diff-filter=ACMR HEAD -- '*.cs'`.
2. Добавить untracked C#-файлы из `git ls-files --others --exclude-standard -- '*.cs'`.
3. Оставить файлы, содержащие добавленные или изменённые реализации, интерфейсы либо базовые типы `GameAction`/`GameEvent`. Для переименований анализировать новое имя файла.
4. Проверять целиком затронутые классы, а не только изменённые строки: изменение одной строки может нарушить контракт существующего метода.
5. Читать неизменённые `GameContext`, event/action и helper-классы, если это необходимо для трассировки вызова. Не сообщать об unrelated ранее существовавших проблемах в неизменённых классах. Если изменённый класс начинает использовать небезопасную неизменённую зависимость, сообщить проблему на строке вызова в изменённом классе.
6. Если подходящих изменённых классов нет, считать проверку дифов успешно выполненной без проблем.

Не изменять файлы во время валидации.

## Проверка `GameAction`

Для каждого действия проверить `Execute` и вызываемые им helpers:

- Разрешить чтение свойств, запросы и проверки `GameContext`, а также возврат `GameActionResult.Failed(...)`.
- Разрешить создание событий и возврат успешного `GameActionResult` с ними.
- Найти прямые присваивания полям/свойствам контекста, изменение коллекций, вызовы mutator-методов и передачу state по `ref`/`out`.
- Проследить aliases: объект, коллекция или state, полученные из контекста, остаются частью контекста. Присваивание их свойствам или вызов изменяющего метода является косвенной мутацией.
- Проследить собственные helper-методы и вызываемые сервисы, если через них может измениться переданный контекст.
- Проверить, что действие валидирует все предусловия, от которых зависит безопасное применение создаваемого события: существование сущностей, допустимость идентификаторов, nullability, диапазоны, фазу и другие бизнес-ограничения.
- Проверить, что событие получает готовые данные изменения и ему не требуется повторно решать, допустимо ли изменение.

## Проверка `GameEvent`

Для каждого события проверить конструктор, `Apply` и вызываемые ими helpers до фактической записи в state:

- Разрешить сохранение payload и безусловное применение изменения к `GameContext`.
- Считать нарушением business guards (`if`/`switch`/условный ранний `return`), которые проверяют допустимость изменения, игнорируют неверные данные или выбирают, применять ли изменение.
- Считать нарушением явные `throw`, assertions, возврат ошибки и вызовы методов, которые могут отклонить данные события.
- Искать не только явные исключения. Индексаторы словарей, `First`/`Single`, небезопасные `Get`, null-разыменование и другие операции с предусловиями считать проблемой, если действие не гарантирует их выполнение, а вызываемый context-метод не реализует безопасную безусловную мутацию.
- Проследить методы `GameContext` и вложенных контекстов, вызванные событием. Валидация или потенциальное падение внутри такого метода также нарушает контракт события.
- Не считать бизнес-валидацией техническое ветвление, которое без риска ошибки выполняет части одного детерминированного изменения. В комментарии отчёта объяснить доказательство, если граница неоднозначна.

## Проверка событийной границы

В режиме `all` дополнительно:

- Убедиться, что state-changing события создаются действиями и возвращаются в `GameActionResult`.
- Сообщить о создании такого события вне `GameAction`, если это не техническая десериализация, replay или доставка уже созданного события.
- Сообщить о мутации `GameContext` из игрового workflow вне `GameEvent`.

Не считать обычное создание объекта при десериализации доказательством нарушения. Устанавливать фактический control flow.

## Формат результата

При отсутствии проблем вернуть ровно одно содержательное предложение для выбранного режима:

- `all`: `Выполнена полная проверка GameAction -> GameContext -> GameEvent. Проблем не обнаружено.`
- `diffs`: `Выполнена проверка дифов GameAction/GameEvent. Проблем не обнаружено.`

При наличии проблем сначала указать выполненный режим, затем вернуть Markdown-таблицу:

| Класс | Строка/строки | Комментарий |
|---|---:|---|
| `ExampleGameAction` | `42–45` | Действие изменяет объект, полученный из `GameContext`; оно должно только проверить данные и создать событие. |

Для каждой независимой проблемы создать отдельную строку. В первой колонке указать имя класса, где находится нарушение. Во второй указать точную строку или минимальный диапазон строк. В третьей кратко объяснить нарушение, прослеженный косвенный вызов при его наличии и ожидаемое разделение ответственности. Не добавлять строки для корректного кода и не предлагать автоматическое исправление без отдельного запроса.
