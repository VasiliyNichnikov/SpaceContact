# Оформление C#-кода

Применяй эти правила ко всему новому и изменяемому C#-коду. Если соседний код им не соответствует, не копируй нарушение. При изменении типа приведи порядок членов всего затронутого типа к этому регламенту, не выполняя несвязанный массовый рефакторинг проекта.

## Версии Unity и C#

Проект использует Unity `6000.3.6f1` (Unity 6.3 LTS) и компилируется с `LangVersion` `9.0`. Целевая версия языка для всего проектного кода — строго C# 9.0: обновление Unity до 6.3 не добавляет поддержку C# 10 и новее.

- Пиши код на C# 9.0: не ограничивай новый код устаревшими соглашениями C# 7 или C# 8, если поддерживаемая конструкция C# 9 делает его понятнее.
- Допустимо использовать поддерживаемые проектом конструкции C# 9, например target-typed `new()` и pattern `is not`.
- Не используй возможности C# 10 и новее. В частности, запрещены file-scoped namespaces, `global using`, `record struct`, `required`, raw string literals, primary constructors и collection expressions.
- Не меняй `LangVersion`, response-файлы компилятора или версию Unity ради использования более нового синтаксиса без отдельного явного запроса программиста.
- Учитывай ограничения Unity 6.3 внутри C# 9: не используй init-only setters, covariant return types, module initializers, подавление флага `localsinit` (`SkipLocalsInit`) и расширяемые соглашения о вызовах для unmanaged function pointers. Последнее ограничение не означает запрет всех unmanaged function pointers.
- Не используй `record`: полной поддержке требуется `System.Runtime.CompilerServices.IsExternalInit`, которого в проекте нет, а Unity Serialization не поддерживает records для сериализуемых типов.

Источники версии внутри репозитория: `ProjectSettings/ProjectVersion.txt` и сгенерированные Unity `.csproj`, во всех которых указано `<LangVersion>9.0</LangVersion>`. Файлы `csc.rsp` включают nullable и не переопределяют версию языка; `Directory.Build.props` также включает nullable и не задает `LangVersion`. При следующем обновлении Unity сверяй эти настройки и ограничения с документацией соответствующей версии Unity; не определяй версию C# по установленному .NET SDK или возможностям Rider.

## Именование

Следуй актуальным соглашениям Microsoft для C#:

- пространства имен, типы, методы, свойства, события и публичные либо защищенные члены — `PascalCase`;
- имена интерфейсов начинаются с `I`, например `IItemFactory`;
- имена атрибутов заканчиваются на `Attribute`;
- параметры методов, параметры конструкторов и локальные переменные — `camelCase`;
- приватные и `internal` поля — `_camelCase` независимо от того, являются ли они статическими, `readonly` или помеченными `[ThreadStatic]`;
- не добавляй статическим полям префиксы `s_` и `t_`: именуй их по тем же правилам, что и остальные поля соответствующего уровня доступа;
- константы при любом уровне доступа, включая локальные константы, — `PascalCase`;
- публичные, `protected`, `protected internal` и `private protected` поля — `PascalCase`;
- параметры обобщенных типов начинаются с `T`: `T`, `TItem`, `TResult`;
- не используй два символа `_` подряд и избегай неочевидных сокращений.

Если поле не должно быть частью публичного API, предпочитай приватное поле. Для сериализации Unity используй `[SerializeField] private`, а не публичное поле без необходимости.

## Числовые литералы

- Не оставляй в коде непонятные числовые литералы («магические числа»), смысл которых нельзя однозначно определить по самой операции.
- Каждое такое значение выноси в именованную `const`-константу. Имя константы должно объяснять назначение числа, единицу измерения или ограничение, которое оно задает.
- Не дублируй одно и то же смысловое число в условиях, вычислениях и аргументах вызовов. Используй одну соответствующую константу.
- Размещай созданные константы в группе константных полей либо объявляй локальной константой, если значение нужно только одному методу.

## Перенос параметров и аргументов

- Не переноси каждый параметр метода или конструктора на отдельную строку по умолчанию.
- Не переноси каждый аргумент вызова метода или конструктора на отдельную строку по умолчанию.
- Пока объявление или вызов помещается в ограничение длины строки, настроенное для C# в Rider, оставляй параметры или аргументы в одной строке.
- Выполняй перенос только тогда, когда строка достигает правой границы Rider. После переноса используй форматирование Rider и сохраняй единообразное выравнивание всего списка.
- Не придумывай отдельное числовое ограничение внутри кода или документации: источником истины является актуальная настройка длины строки в Rider.

## Файлы и объявления типов

- Каждый самостоятельный `class`, `struct` и `enum` объявляй в отдельном `.cs`-файле. Это же правило применяй к самостоятельным интерфейсам и делегатам.
- Имя файла должно точно совпадать с именем объявленного в нем основного типа.
- Не размещай несколько самостоятельных типов в одном файле, даже если они небольшие или используются вместе.
- Вложенный тип допустим только тогда, когда он объявлен `private` и является исключительно деталью реализации содержащего его типа. Если тип должен быть доступен снаружи, вынеси его в отдельный файл. Исключение — валидатор и enum ошибок конкретного `GameAction` по разделу 1.1 `docs/CSharpCodeStyle.md`: класс `Validator` и enum объявляются внутри action, в том же файле, с минимально необходимым уровнем доступа.

### Запрет partial

- Не создавай `partial class`, `partial struct`, `partial interface` и `partial`-методы в проектном коде.
- Не используй `partial` для разбиения большого типа, группировки методов, реализации нескольких интерфейсов или обхода правил порядка членов. Вместо этого разделяй ответственности между обычными типами и файлами.
- Единственное исключение — техническое требование сторонней библиотеки, генератора кода или протокола интеграции, когда без `partial` интеграция не работает. Пример: генерируемая интеграция MessagePack.
- В исключительном случае используй `partial` только в минимально необходимом объеме и не распространяй этот подход на остальной проектный код.

## Порядок членов типа

Внутри каждого `class`, `struct` или `interface` располагай группы в следующем порядке (StyleCop SA1201 и SA1203):

1. Константные поля (`const`)
2. Остальные поля
3. Конструкторы
4. Финализаторы (деструкторы)
5. Делегаты
6. События
7. Перечисления (`enum`)
8. Вложенные интерфейсы
9. Свойства
10. Индексаторы
11. Методы
12. Вложенные структуры
13. Вложенные классы

Не смешивай группы. Реализация интерфейса не является отдельным видом члена: ее свойства, события и методы остаются в соответствующих группах.

### Порядок по доступу

Внутри каждой группы сортируй члены по уровню доступа (SA1202):

1. `public`
2. `internal`
3. `protected internal`
4. `protected`
5. `private protected`
6. `private`

### Порядок static и readonly

Внутри каждого уровня доступа сначала размещай статические, затем нестатические члены (SA1204).

Для полей внутри каждой статической или нестатической подгруппы сначала размещай `readonly`, затем изменяемые поля (SA1214 и SA1215). Таким образом, обычные поля одного уровня доступа идут в порядке:

1. `static readonly`
2. `static`
3. instance `readonly`
4. instance non-readonly

`const` всегда остается в отдельной первой группе константных полей.

### Развернутый порядок методов

1. `public static`
2. `public`
3. `internal static`
4. `internal`
5. `protected internal static`
6. `protected internal`
7. `protected static`
8. `protected`
9. `private protected static`
10. `private protected`
11. `private static`
12. `private`

Эту же схему доступа и статичности применяй к другим группам членов.

Если члены нескольких реализуемых интерфейсов хочется сохранить рядом, все равно соблюдай общий порядок свойств, событий и методов. Не создавай для группировки `partial`-части типа.

## Nullable-контракты

В проекте включен nullable reference types. Аннотация nullability является обязательной частью контракта:

- Не добавляй `#nullable enable` в отдельные `.cs`-файлы. Nullable уже централизованно включен параметром `-nullable:enable` в `csc.rsp` каждой проектной сборки.
- Не дублируй настройку из `csc.rsp` директивами на уровне файла и не пытайся локально переключать nullable-контекст без отдельного явного запроса программиста.

- `T` без `?` никогда не должен содержать, принимать или возвращать `null`;
- `T?` явно означает, что `null` является допустимым значением;
- вызывающий код вправе использовать значение типа `T` без дополнительной проверки на `null`;
- не проверяй значение типа `T` на `null`: такая проверка противоречит объявленному контракту и скрывает ошибку инициализации;
- проверки `is null`, `== null`, `!= null`, а также null-conditional и null-coalescing операции применяй только к значениям, в типе которых явно указан `?`;
- значение типа `T?` должно быть проверено или обработано до разыменования;
- не добавляй `?` только для подавления предупреждения — исправляй инициализацию или уточняй реальный контракт;
- оператор подавления `!` не меняет runtime-значение и допустим только там, где ненулевое значение гарантированно назначается внешним механизмом до первого чтения.

Для `[SerializeField]` в `MonoBehaviour` различай обязательные и опциональные ссылки:

- Если поле non-nullable и Inspector обязан его назначить, используй `= null!`. Не создавай фиктивный объект или пустую коллекцию через `new()` только для подавления предупреждения nullable.
- Если поле nullable и отсутствие значения допустимо, оставляй его без инициализатора. Не добавляй ни `= null!`, ни `= new()`.

Обязательное поле:

```csharp
[SerializeField]
private int[] _contentSpan = null!;
```

Опциональное поле:

```csharp
[SerializeField]
private SortingOrderStaticSegment[]? _segments;
```

Не добавляй для такой non-nullable ссылки защитную проверку на `null`. Если отсутствие ссылки действительно является допустимым runtime-состоянием, объяви ее как nullable (`T?`) и явно обработай этот сценарий. Если `null` недопустим, исправь источник значения или порядок инициализации.

Правила распространяются на поля, свойства, параметры, возвращаемые значения, элементы коллекций и generic-аргументы. Не возвращай `null` из члена с non-nullable типом и не присваивай `null` non-nullable полю ни на одной ветке выполнения.

## Unity-состояния, логирование и исключения

- Не добавляй защитные проверки `gameObject.activeInHierarchy` на каждом шаге выполнения. Проверяй это свойство только тогда, когда активность объекта действительно изменяет требуемую ветку поведения.
- Не считай неактивный `GameObject` исключительной ситуацией и не выбрасывай исключение только из-за `activeInHierarchy == false`.
- Под логгером в этом регламенте всегда подразумевается статический класс `Logs.Logger` из `Assets/Scripts/Logs/Logger.cs`. Подключай `using Logs;`; при конфликте имен используй полное имя `Logs.Logger`.
- Вызывай `Logger.Error(string message)` для ошибок, `Logger.Warning(string message)` для предупреждений и `Logger.Log(string message)` для информационных сообщений.
- В коде `MonoBehaviour` и ViewModel не выбрасывай исключения для сообщения об ошибочном состоянии. Вызывай `Logger.Error(...)` для ошибки, из-за которой операцию нельзя корректно продолжить, либо `Logger.Warning(...)` для некритичного отклонения.
- Потребители используют статический `Logger` напрямую: не внедряй `ILogger` через DI, не добавляй поле `_logger` и не создавай `UnityLogger`. Выбор и создание реализации уже выполняются внутри `Logger`.
- `Logger.CriticalError(string message)` сейчас вызывает тот же метод реализации, что и `Logger.Error(...)`; не рассчитывай на остановку выполнения или выброс исключения. `Logger.Todo(...)` доступен только под `UNITY_EDITOR` и помечен `Obsolete`; не используй его в новом коде.
- Не обходи проектный `Logger` прямыми вызовами `UnityEngine.Debug.Log`, `Debug.LogWarning` или `Debug.LogError` в потребителях. Такие вызовы допустимы внутри реализации логгера.
- После логирования безопасно заверши текущую операцию или продолжи по предусмотренной ветке. Не дублируй одинаковую проверку и одинаковое сообщение на каждом уровне вызовов.

## Конструкторы

- Конструктор только принимает зависимости и начальные данные и присваивает их членам объекта. Зарегистрированные зависимости передает VContainer; не выполняй в конструкторе другую логику.
- Не валидируй аргументы и данные внутри конструктора.
- Не выбрасывай из конструктора `ArgumentNullException`, `ArgumentException`, `InvalidOperationException` и другие исключения.
- Не используй в присваиваниях конструктора выражения вида `argument ?? throw ...`.
- Если данным нужна отдельная проверка, выполняй ее вне конструктора в предназначенном для этого валидаторе или на уровне сценария, который создает объект.

## Инъекция зависимостей через VContainer

В проекте используется VContainer (`jp.hadashikick.vcontainer` в `Packages/manifest.json`). Его API: `IContainerBuilder` для регистрации и `IObjectResolver` для разрешения зависимостей. Отдельного типа `DiContainer` в проекте нет.

- Регистрируй зависимости в `Configure(IContainerBuilder builder)` соответствующего `LifetimeScope`: `ProjectLifeScope` для уровня приложения и `GameLifetimeScope` для уровня игры. Выбирай `Lifetime` по требуемому жизненному циклу объекта.
- Для обычных C#-классов используй инъекцию типизированных зависимостей через конструктор и сохраняй их в `readonly`-полях. VContainer сам передает зарегистрированные зависимости; вручную повторять список `Resolve<T>()` в фабрике регистрации не требуется.
- Сохраняй установленный в изменяемом типе способ инъекции. В проектных ViewModel также используется `[Inject]` на полях. Большое количество зависимостей само по себе не требует передачи контейнера в конструктор.
- Для `MonoBehaviour` используй метод с `[Inject]`, как в существующих View и сетевых компонентах. Обеспечь инъекцию через регистрацию компонента, `IObjectResolver.Instantiate(...)` или существующую инфраструктуру инъекции. Сам по себе атрибут `[Inject]` не запускает инъекцию.
- Обязательные ссылочные поля, назначаемые через `[Inject]`, инициализируй `= null!` и используй только после инъекции. Поля и методы с `[Inject]` заполняются после конструктора; не читай такие зависимости в конструкторе.
- Передавай `IObjectResolver` фабрикам и инфраструктурным сервисам, которым действительно нужно создавать объекты с инъекцией или разрешать динамические зависимости. Для создания Unity-префабов используй `resolver.Instantiate(...)` из `VContainer.Unity`, как в `DialogsFactory` и `GameShipsOnPlanetInfoViewFactory`.
- Не используй контейнер как service locator в обычных методах: известные заранее зависимости внедряй явно. Сохраняй `IObjectResolver` в поле только тогда, когда он нужен после создания объекта, например фабрике префабов.

Пример инъекции через конструктор (каждый тип размещается в отдельном файле):

```csharp
public sealed class GameViewService
{
    private readonly GameContext _context;

    public GameViewService(GameContext context)
    {
        _context = context;
    }
}
```

Регистрация внутри `Configure(IContainerBuilder builder)` при уже зарегистрированном `GameContext`:

```csharp
builder.Register<GameViewService>(Lifetime.Singleton).AsSelf();
```

Для регистрации по контракту используй `.As<TInterface>()` или `.AsImplementedInterfaces()`, как в существующих `LifetimeScope`. Для готовых объектов и компонентов используй `RegisterInstance(...)` и `RegisterComponent(...)` соответственно.

## Самопроверка перед завершением

- Код совместим с Unity `6000.3.6f1` и C# 9.0 и не содержит синтаксиса C# 10 или новее либо неподдерживаемых Unity 6.3 возможностей C# 9.
- Все новые и переименованные идентификаторы соответствуют правилам именования.
- В коде нет непонятных числовых литералов: все магические числа вынесены в осмысленно названные константы.
- Параметры и аргументы не переносятся построчно, пока выражение помещается в настроенную в Rider длину строки.
- Каждый самостоятельный тип находится в отдельном одноименном файле; вложенные типы соответствуют общему правилу `private` либо специальному правилу для `Validator` и enum ошибок внутри `GameAction`.
- В проектном коде нет новых `partial`-типов или методов без обязательного требования сторонней библиотеки либо генератора кода.
- Члены каждого затронутого типа отсортированы по виду, доступу, `static` и `readonly`.
- Все non-nullable значения действительно инициализированы и не могут стать `null`.
- В `.cs`-файлах нет лишней директивы `#nullable enable`: nullable включен через проектные `csc.rsp`.
- В коде нет проверок non-nullable значений на `null`.
- Каждая `?` отражает допустимый сценарий, а не скрывает ошибку проектирования или инициализации.
- Обязательные non-nullable `[SerializeField]`-ссылки и коллекции имеют `= null!`, а опциональные nullable поля объявлены без инициализатора; ни те, ни другие не инициализируются через `new()`.
- В `MonoBehaviour` и ViewModel ошибочные состояния логируются через статический `Logs.Logger`, а не превращаются в исключения.
- Потребители используют `Logger.Error(...)`, `Logger.Warning(...)` и `Logger.Log(...)`, не внедряют логгер через DI, не создают его реализацию и не обходят его вызовами `UnityEngine.Debug`.
- Конструкторы не содержат валидации аргументов и не выбрасывают исключения.
- Зависимости внедряются через VContainer: конструкторы или установленный в типе `[Inject]`; `IObjectResolver` используется только там, где требуется создание объектов с инъекцией или динамическое разрешение зависимостей.

## Отмена асинхронных операций

- Отмена — обычный исход операции. В проектном коде не использовать `OperationCanceledException` (включая `TaskCanceledException`) для управления выполнением: не бросать и не перехватывать эти исключения.
- Не вызывать `ThrowIfCancellationRequested`, не возвращать отменённые Task через `Task.FromCanceled`, `SetCanceled` или `TrySetCanceled`.
- Проверять `IsCancellationRequested` явно до начала работы и после `await`, прежде чем применять результат или изменять состояние. При отмене завершать метод обычным `return`; для методов с результатом явно определить представление отмены в контракте.
- Освобождать ресурсы и очищать pending в `finally`, независимо от исхода операции. Отмена ожидания не означает откат уже выполненного действия.
- Не передавать токен в API, которое при его отмене выбрасывает исключение или возвращает отменённый Task. Для такого API организовать обычное завершение ожидания при отмене, игнорировать поздний результат и наблюдать возможные ошибки оставшейся операции. Проверка токена после `await` сама по себе не предотвращает исключение из отменённого Task.
