# Регламент оформления C#-кода для агента

Этот документ обязателен при создании и изменении C#-кода в проекте. Перед завершением задачи агент должен проверить изменённые файлы на соответствие всем правилам ниже.

## 1. Именование и оформление

При написании C#-кода необходимо следовать официальным соглашениям Microsoft по именованию и оформлению C#.

Основные требования:

- типы, пространства имён, методы, свойства, события и публичные или защищённые члены именуются в `PascalCase`;
- локальные переменные и параметры именуются в `camelCase`;
- приватные поля именуются в `_camelCase`;
- публичные и защищённые поля именуются в `PascalCase`;
- имена интерфейсов начинаются с `I`, например `IGameService`;
- имена не должны содержать венгерскую нотацию и неинформативные сокращения;
- имя должно ясно отражать назначение сущности;
- для асинхронных методов используется суффикс `Async`, если метод возвращает `Task`, `Task<T>`, `ValueTask` или `ValueTask<T>` и не является реализацией уже заданного контракта с другим именем.

Если правила этого документа не уточняют конкретный случай, применяется актуальное официальное руководство Microsoft по стилю C#.

## 2. Порядок членов типа

Внутри `class`, `struct` или `interface` члены располагаются по категориям в следующем порядке согласно StyleCop SA1201 и SA1203:

1. константные поля (`const`);
2. поля;
3. конструкторы;
4. финализаторы (деструкторы);
5. делегаты;
6. события;
7. перечисления (`enum`);
8. интерфейсы и реализации интерфейсов;
9. свойства;
10. индексаторы;
11. методы;
12. вложенные структуры (`struct`);
13. вложенные классы (`class`).

### 2.1. Порядок по уровню доступа

Внутри каждой категории члены располагаются по уровню доступа согласно StyleCop SA1202:

1. `public`;
2. `internal`;
3. `protected internal`;
4. `protected`;
5. `private protected`;
6. `private`.

### 2.2. Статические и экземплярные члены

Внутри каждой группы с одинаковым уровнем доступа сначала размещаются статические, затем экземплярные члены согласно StyleCop SA1204:

1. `static`;
2. non-static.

### 2.3. Поля `readonly`

В каждой группе полей с одинаковыми уровнем доступа и статичностью сначала размещаются поля `readonly`, затем остальные поля согласно StyleCop SA1214 и SA1215:

1. `readonly`;
2. non-readonly.

### 2.4. Пример порядка методов

Методы располагаются в следующем порядке:

1. `public static`;
2. `public`;
3. `internal static`;
4. `internal`;
5. `protected internal static`;
6. `protected internal`;
7. `protected static`;
8. `protected`;
9. `private protected static`;
10. `private protected`;
11. `private static`;
12. `private`.

Эти же правила группировки по доступу и статичности применяются к остальным категориям членов.

### 2.5. Реализация нескольких интерфейсов

Если предписанный порядок мешает сохранить связанность реализаций нескольких интерфейсов, следует использовать `partial class`. Свойства и методы одной реализации интерфейса можно вынести в отдельную часть класса и сгруппировать вместе.

## 3. Nullable reference types

В проекте включён nullable-контекст. Аннотации nullable являются обязательной частью контракта, а не подсказкой.

- Ссылочный тип без `?` никогда не должен содержать или возвращать `null`.
- Ссылочный тип с `?` имеет право содержать или возвращать `null`; вызывающий код обязан корректно обработать этот случай.
- Нельзя возвращать `null` из метода, свойства или функции с non-nullable возвращаемым типом.
- Нельзя присваивать `null` non-nullable полю, свойству, параметру или локальной переменной.
- Non-nullable поля должны быть гарантированно инициализированы до первого чтения.
- Нельзя скрывать нарушение контракта с помощью оператора подавления предупреждения `!` без доказуемой гарантии non-null значения.
- Нельзя добавлять `?` только ради устранения предупреждения компилятора. Nullable-аннотация должна отражать реальную семантику данных.
- Проверки на `null` должны сохраняться там, где значение объявлено nullable или поступает из внешнего API без надёжного nullable-контракта.

Пример:

```csharp
private readonly IGameService _gameService;
private PlayerState? _selectedPlayer;

public PlayerState CurrentPlayer { get; private set; }

public PlayerState? FindPlayer(Guid playerId)
{
    // Метод явно сообщает, что игрок может быть не найден.
}
```

В этом примере `_gameService` и `CurrentPlayer` всегда обязаны иметь non-null значение, а `_selectedPlayer` и результат `FindPlayer` могут быть `null`.

## 4. Проверка перед завершением задачи

Перед завершением изменений агент обязан убедиться, что:

- новые и изменённые идентификаторы соответствуют соглашениям Microsoft и правилам этого документа;
- члены каждого затронутого типа расположены в установленном порядке;
- nullable-аннотации точно отражают контракт;
- ни один non-nullable член не может получить или вернуть `null`;
- оператор `!` не используется для маскировки потенциального `null`;
- исключение из порядка членов для реализаций интерфейсов оформлено через обоснованное разделение на `partial class`.
