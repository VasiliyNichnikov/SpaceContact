# TODO: единый объект статичных данных и правил для GameContext

Статус: идея для обсуждения по запросу пользователя. Названия и контракт ниже предварительные; реализация пока не выполняется.

## Проблема

После C12 `GameContext` получает `GamePhaseDurationData` через конструктор и открывает его через `PhaseDurations`. `StartReadyTransitionTimerGameAction` использует эти данные для расчёта ready deadline.

Если добавлять таким способом каждый набор настроек, конструктор и свойства контекста будут расширяться при появлении новых правил. Нужно рассмотреть отдельный класс, который объединяет статичные данные партии и передаётся в контекст одной зависимостью.

## Предлагаемое направление

Рабочее имя — `GameStaticData`. Он содержит типизированные разделы правил и настроек, например `PhaseDurations`, а `GameContext` предоставляет доступ к нему через свойство `StaticData`.

Пример предполагаемого обращения: `context.StaticData.PhaseDurations.ReadyTransitionDurationInSeconds`.

В конструктор контекста передаётся один `GameStaticData`. Добавление нового раздела требует изменения состава этого класса и его сборки, но не расширяет конструктор `GameContext`. Это явно описанный набор данных с именованными свойствами; словарь объектов и разрешение произвольных зависимостей через `Get<T>()` не требуются.

Под «статичными» здесь понимаются данные, неизменные в течение партии. Это обычный экземпляр класса, а не глобальный `static` singleton. Разные партии могут использовать разные настройки.

## Состав и границы

Первый кандидат на перенос — `GamePhaseDurationData`. Другие разделы добавлять после проверки реальных потребителей: например, определения карт и числовые правила, необходимые Actions. Не требуется сразу переносить все существующие конфиги проекта.

В объект входят значения правил и определения, а не текущее игровое состояние. Readiness игроков, текущие дедлайны, колоды, руки, выбранные цели и revision остаются в изменяемых разделах `GameContext` и обновляются через события.

Часы, локальная идентичность игрока, транспорт и другие сервисы не являются статичными правилами. Их не следует автоматически включать в этот класс ради сокращения списка параметров. Существующий `IGameDataProvider` предоставляет `LocalPlayerId`; нужно отдельно решить, сохраняется ли его имя, чтобы не путать его с новым набором правил.

Core должен получать обычные данные без ссылок на Unity `ScriptableObject`, префабы или UI. Преобразование конфигов и создание полного объекта выполняются на стороне сборки зависимостей игры. Сейчас `GameConfigs.Build` уже регистрирует результат `GamePhaseDurationConfig.BuildData`; это одно из мест, которое понадобится пересмотреть при реализации.

## Вопросы для обсуждения

- [ ] Выбрать имя класса и свойства контекста: `GameStaticData` / `StaticData`, `GameRulesData` / `Rules` либо другой вариант.
- [ ] Определить первый состав разделов и проверить, какие из них действительно нужны действиям через контекст.
- [ ] Выбрать создание объекта: конструктор с типизированными разделами либо отдельная фабрика, если сборка требует подготовки данных. Не переносить большой список ручных `Resolve<T>()` внутрь контекста.
- [ ] Зафиксировать неизменяемость на время партии. Одних get-only свойств недостаточно, если вложенные коллекции можно изменить извне; определить владение и доступ к таким коллекциям.
- [ ] Определить момент проверки полноты и корректности конфигурации до запуска партии. Сохранить существующее правило: конструкторы только принимают и сохраняют данные.
- [ ] Решить, могут ли server/client контексты host разделять один неизменяемый экземпляр. Если появятся серверные закрытые настройки, определить отдельный доступный клиенту набор.
- [ ] Определить, как клиенты получают согласованные с сервером правила: локальные конфиги, версия набора или передача данных при запуске. Само добавление класса эту задачу не решает.
- [ ] Решить, какие потребители получают отдельные разделы через DI, а какие читают их через `GameContext`, чтобы избежать двух расходящихся наборов правил.

## Возможный порядок реализации

1. Выбрать контракт и состав объекта на примере длительностей фаз.
2. Собрать объект из существующих конфигов и зарегистрировать его на время игровой сессии.
3. Заменить отдельный параметр `GamePhaseDurationData` в `GameContext` общим объектом; обновить чтение длительности ready timer.
4. Проверить другие места создания контекста и потребителей данных. Новые разделы добавлять по необходимости.

## Критерии готовности будущей задачи

- Добавление раздела статичных правил не требует нового параметра конструктора `GameContext`.
- Доступ к данным типизирован; обязательные разделы доступны сразу после создания контекста.
- Изменение Unity-конфига или исходной коллекции после создания партии не меняет её правила неожиданно.
- Статичные настройки не становятся частью изменяемого snapshot и не меняют revision сами по себе.
- Сервер рассчитывает ready deadline по выбранной конфигурации; при текущем значении сохраняется интервал 3 секунды.
- Контексты разных партий могут использовать разные наборы правил без взаимного влияния.

Это отдельный архитектурный вопрос. Документ не утверждает окончательное решение и не расширяет реализацию C12 или C13.
