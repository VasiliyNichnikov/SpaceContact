# Переходы между фазами и валидация данных

**Статус:** под вопросом. Архитектурное решение не выбрано; реализация отложена.

## Проблема

Проверки данных отдельных фаз внутри `TransitionToNextPhaseGameAction` заставляют общий action расти при добавлении каждой новой фазы. Из него удалены условия выхода из FirstMove (наличие aggressor) и Destiny (наличие aggressor, defender и planet). Перенос этих условий в новый общий switch не решает проблему расширения.

Сейчас action проверяет только серверные права, исходную фазу и revision, новую revision, допустимость перехода по существующему графу, наличие участников и наступление срока перехода. Проверки времени на NaN, Infinity и отрицательные значения удалены по решению пользователя: корректность времени предполагается контрактом. Проверки других actions и snapshots этим изменением не затрагиваются.

**Текущее ограничение:** сам transition action больше не гарантирует выполнение обязательного действия фазы. В частности, он не блокирует выход из FirstMove без aggressor или из Destiny без полной цели. Игровое требование завершить обязательное действие перед выходом сохраняется; способ его обеспечения предстоит определить.

## Что предстоит решить

- Где описывать разрешённые переходы и условия выхода/входа, чтобы новая фаза не требовала новых веток в общем action.
- Кто проверяет полноту и допустимость данных конкретной фазы и как сообщает причину отказа.
- Как связать проверку с серверным автодействием C13: определить необходимость автодействия, выполнить его через actions/events и проверить возможность перехода после применения результата.
- Как разделить игровые условия, таймеры и ACK входных данных, сохранив единственный серверный путь исполнения и согласованные revision.

Возможные направления обсуждения — отдельные правила фаз, реестр правил или описание переходов с подключаемыми проверками. Ни один вариант пока не согласован; новые интерфейсы и реализации в рамках этой правки не добавляются.

## Критерии будущего решения

- Общий transition action не содержит условий для конкретных фаз.
- Невыполненное обязательное действие блокирует выход, включая переход по основному таймеру и ready timer.
- Проверки не изменяют контекст; изменения выполняются через actions/events. События применяют готовые данные без выбора правил перехода.
- Отказ сохраняет состояние и revision; устаревшая команда не применяется к новому входу.
- Новая фаза подключает свои правила без расширения цепочки проверок по enum в общем action.
