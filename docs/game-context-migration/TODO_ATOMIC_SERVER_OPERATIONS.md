# TODO: атомарное выполнение серверных операций

Статус: отложено по решению пользователя. Реализация в рамках этой записи не выполняется.

- [ ] Пересмотреть обработку исключений в C06: ошибка отдельной операции не должна без необходимости завершать игровую сессию.

## Проблема текущей реализации

`GameActionExecutor` применяет события непосредственно к живому `GameContext`. Если action, event или построение клиентской проекции выбрасывает исключение, context получает `IsOperationFaulted = true`. Следующие операции, загрузка и выдача snapshots запрещаются. Автоматического восстановления нет; для продолжения требуется новый context/executor.

Остановка защищает от продолжения игры из частично изменённого состояния, но слишком груба: даже исключение до применения первого события блокирует всю сессию. Простое удаление флага или перехват исключения с продолжением исполнения проблему частичных изменений не решает.

Обычный отказ `GameActionResult.Failed(...)` не блокирует сессию. Ошибки подписчиков `StateChanged` после commit и ошибки сетевой доставки также следует отличать от ошибок подготовки операции: состояние уже принято, повторно применять его нельзя.

## Предлагаемое направление

Подготавливать операцию в изолированном временном состоянии и устанавливать результат только после успешного применения всех событий и подготовки всех клиентских проекций.

1. Проверить отправителя, action ID и повтор принятого действия.
2. Выполнить проверку action и применение событий так, чтобы исключение не затронуло живое состояние. Временные коллекции и изменяемые объекты не должны разделяться с живым context.
3. Подготовить итоговое состояние, целевую revision и batches всех получателей до commit. Во время подготовки не вызывать наблюдателей живого context и не начинать доставку.
4. Установить подготовленный результат, зафиксировать revision и результат для защиты от повторов, затем уведомить наблюдателей. Сам commit не должен содержать этапов подготовки, способных оставить частично установленное состояние.
5. При ошибке до commit отбросить временные данные, сохранить прежние state/revision и вернуть ошибку операции. Следующая корректная операция должна оставаться доступной.

Конкретный механизм изоляции и установки выбрать при реализации. Согласовать его с [пересмотром ручного ReplaceState](PLAN.md#13-пересмотреть-ручную-замену-состояния-через-replacestate): не создавать второй ручной список переносимых полей. Сохранить подписки либо определить явный контракт их обновления. Оценить стоимость подготовки полного snapshot на каждой операции.

Отдельно определить обработку ошибки самого commit: продолжение допустимо только при гарантированной целостности состояния. Атомарная подготовка не должна маскировать повреждение живого context.

## Критерии готовности

- [ ] Исключение в action до первого event не меняет состояние/revision и не блокирует следующую корректную операцию.
- [ ] Исключение в середине списка events оставляет живое состояние полностью прежним.
- [ ] Ошибка проекции для любого получателя отменяет всю подготовку; ни один batch не отправлен.
- [ ] Неуспешная подготовка не вызывает уведомлений живого состояния и не сохраняется как принятая операция в кеше повторов.
- [ ] Успешная операция устанавливает все изменения с одной revision; наблюдатели видят согласованный итог.
- [ ] Повтор принятого action не применяет изменения ещё раз, включая повтор после ошибки уведомления или доставки.
- [ ] Защита от вложенного исполнения из callbacks сохраняется.
- [ ] Проверки подтверждают отсутствие общих изменяемых коллекций между временным и живым состоянием, сохранение подписок и возможность продолжить после неуспешной подготовки.
