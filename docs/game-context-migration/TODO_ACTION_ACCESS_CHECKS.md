# TODO: общие проверки роли контекста и прав actor в Actions

Статус: отложено по запросу пользователя. Сейчас фиксируется проблема; реализация helper и изменение Actions не выполняются.

## Проблема

В игровых Actions повторяются проверки `context.Role == GameContextRole.Server` и `actor.IsSystem`. Они смешиваются с проверками фазы, существования участника и соответствия actor текущему агрессору. При добавлении нового action приходится заново писать условия и сообщения об ошибках; легко пропустить проверку или получить разные правила для одинаковых операций.

Примеры по исходникам на 18 октября 2026 года (пути относительно `Assets/Scripts/Core/Game/Actions`):

| Место | Текущая проверка |
|---|---|
| `StartEncounterGameAction.Execute` | Server и system; отдельно FirstMove. |
| `ChooseDestinyCardGameAction.Execute` / `CreateSelectionResult` | System на входе; Server и Destiny при подготовке выбора. |
| `SkipDestinyCardGameAction.Execute` | Server и Destiny; actor — system или текущий агрессор. |
| `SelectTargetPlanetGameAction.CheckRoleAndPhase` / `CheckActor` | Server и Destiny; actor — system или текущий агрессор. Проверки уже разбиты на методы, но дублирование между Actions осталось. |
| `GameActionExecutor.Execute` | Для несистемного actor проверяются наличие PlayerId и участие в игре. |

Кроме того, executor вызывает `GameContext.BeginServerOperation`, который уже запрещает исполнение на контексте с ролью, отличной от Server. Это нужно учесть при выборе общего места проверки: сейчас нарушение на инфраструктурном уровне вызывает исключение, а проверки внутри Actions возвращают обычный отказ.

- [ ] Выбрать небольшой общий helper либо несколько составных проверок для Server, system и system/агрессора. Имена и API пока не утверждены.
- [ ] Определить, стоит ли включать проверку фазы в helper или оставить её отдельным игровым предусловием.

- [ ] После выбора решения заменить повторяющиеся условия в Actions и проверить порядок отказов и сообщения.

## Ограничения будущего решения

Server и system — разные условия: первое описывает роль контекста, второе — инициатора операции. Игрок может выполнять разрешённое действие на серверном контексте; system не должен автоматически получать право выполнить любое действие в любой фазе.

Не сводить все Actions к требованию `IsSystem`: выбор цели и skip разрешены также агрессору, а ready относится к конкретному участнику. Существование игрока и совпадение с агрессором также являются разными проверками.

Helper только проверяет предусловия и возвращает результат. Он не меняет context, не применяет события и не выбирает игровые цели. Правила карты, планеты и присутствия вражеских кораблей остаются в соответствующей игровой логике.

Сохранить серверное определение actor по отправителю запроса: клиент не должен задавать `IsSystem`. При переносе проверок в executor отдельно учесть внутренние вызовы и не оставить путь обхода авторизации.

## Критерии готовности будущей задачи

- Повторяемые правила доступа имеют один источник реализации.
- System-only Actions отклоняют игроков; действия агрессора принимают только разрешённых инициаторов; неизвестный участник отклоняется.
- Клиентский context не допускается к серверным действиям, в том числе через внутренние пути подготовки результата.
- Отказ не создаёт событий и не меняет состояние или revision.
- Ручной и автоматический выбор сохраняют одинаковые игровые правила.
- Рефакторинг не меняет допустимые действия, порядок значимых проверок и поведение повторных запросов без отдельного решения.

Сценарии здесь — требования будущей проверки, а не уже выполненные тесты. Эта запись не добавляет реализацию в C10 и не меняет порядок следующих этапов миграции.
